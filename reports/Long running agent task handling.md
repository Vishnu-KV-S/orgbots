# Budgets and progress audits replace step caps

No production long-horizon agent studied here ends work because it reached a small fixed number of steps. OpenAI's Codex Goals, xAI's Grok Bot, LangGraph's current defaults and open-source browser agents all keep a step count only as a large runaway guard. What actually ends a task is one of four things: a **token, time or cost budget** that triggers a graceful wrap-up turn; a **progress classification** that marks the task "blocked" only after the same blocker repeats several times; an **evidence-based completion audit**; or a **human pause**. Around that core they use the same supporting machinery: structured handoff summaries and observation masking to keep context bounded, waits on slow jobs that cost no model calls, malformed output fed back to the model as an error instead of ending the run, and procedural "skills" distilled from successful runs. The best-measured of these is skill reuse, which lifted WebArena success by 31–51% relative in two studies. For the in-house DeepSeek/LangGraph bot, the 24-step × 5-chunk ceiling should become a task-level budget with a 75% warning and a forced final step. Chunk boundaries should become checkpoint-and-compaction boundaries rather than stop points. The 20-step "wait 30s" pattern should become a harness-driven wait that makes no LLM calls. The XML-tag failure is almost certainly DeepSeek's documented DSML tool-call leakage, and native strict tool calls plus a layered parser fix it. The bot's current worst-case spend (5 chunks × $3, 5 × 30 min) can stay the same. The change is that it gets spent only while the task is making progress.

## Step caps survive only as runaway guards with graceful exits

The vendors split cleanly between short-agent defaults and long-horizon products. OpenAI's Agents SDK still defaults to **`max_turns = 10`** in both Python and JS, and exceeding it raises `MaxTurnsExceeded` ([run_config.py](https://github.com/openai/openai-agents-python/blob/main/src/agents/run_config.py), [constants.ts](https://github.com/openai/openai-agents-js/blob/main/packages/agents-core/src/runner/constants.ts)). That cap can be removed with `max_turns=None`, or softened with a `"max_turns"` error handler that returns a final output in place of the exception ([Running agents](https://openai.github.io/openai-agents-python/running_agents/)). For the raw computer-use tool, OpenAI sets no number at all. It tells integrators to "set step, time, or cost limits, support cancellation, and check the actual outcome" ([Computer use guide](https://developers.openai.com/api/docs/guides/tools-computer-use)). Codex, OpenAI's real long-horizon product, has **no turn or step key in its config**. Long work runs under `/goal`, with "persisted goals and automatic continuation" on by default and optional token budgets under `features.rollout_budget` ([Codex config reference](https://learn.chatgpt.com/docs/config-file/config-reference)).

The way budget exhaustion is handled matters as much as the budget itself. When a Codex goal reaches its budget, the runtime marks it `budget_limited` and injects a template telling the model to "not start new substantive work… summarize useful progress, identify remaining work or blockers, and leave the user with a clear next step" ([budget_limit.md](https://github.com/openai/codex/blob/main/codex-rs/ext/goal/templates/goals/budget_limit.md)). OpenAI's cookbook adds that "reaching a budget limit is not the same as completing the objective" ([Using Goals in Codex](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)). xAI behaves the same way at its cap. The API's `max_turns` counts assistant turns, not tool calls. When it is reached, the agent "stops making tool calls and generates a final response from the information gathered so far" instead of erroring ([xAI Tool usage details](https://docs.x.ai/developers/tools/tool-usage-details)). A client-side tool call ends the request, and the follow-up request starts with a fresh turn count, so each request is a budgeted segment of a longer run ([xAI Advanced tool usage](https://docs.x.ai/docs/guides/tools/advanced-usage)). Grok Bot, xAI's computer-use product, publishes **no per-task step or time limit** at all. Bots "keep working 24/7" and are bounded only by weekly usage and spending limits ([Introducing Grok Bot](https://x.ai/news/introducing-grok-bot), [Grok Bot FAQ](https://docs.x.ai/grok-bot/faq)).

LangGraph has moved the same way. `recursion_limit` caps supersteps **per invocation, not per thread**. The docs say the default is 1000 since 1.0.6, but the shipped 1.2.14 source sets `DEFAULT_RECURSION_LIMIT` to **10007**, and both LangChain's `create_agent` and Deep Agents pin it to 9_999 ([Graph API docs](https://docs.langchain.com/oss/python/langgraph/graph-api), [_config.py](https://github.com/langchain-ai/langgraph/blob/main/libs/langgraph/langgraph/_internal/_config.py), [factory.py](https://github.com/langchain-ai/langchain/blob/master/libs/langchain_v1/langchain/agents/factory.py)). The counter is set relative to the step a run starts from, so **resuming the same thread gets a fresh budget** ([pregel/_loop.py](https://github.com/langchain-ai/langgraph/blob/main/libs/langgraph/langgraph/pregel/_loop.py)). LangGraph's recommended pattern is to declare `RemainingSteps` in state and route to a wrap-up node when it gets low, so the graph "completes normally" with a checkpoint instead of raising `GraphRecursionError` ([Graph API docs](https://docs.langchain.com/oss/python/langgraph/graph-api)). Step bounding in the v1 agents now lives in `ModelCallLimitMiddleware` and `ToolCallLimitMiddleware`. Both separate a persisted `thread_limit` from a per-invocation `run_limit` ([model_call_limit.py](https://github.com/langchain-ai/langchain/blob/master/libs/langchain_v1/langchain/agents/middleware/model_call_limit.py)). LangChain ships no wall-clock or cost-ceiling middleware, so those remain custom code.

browser-use is the closest open-source analogue to the in-house bot, and it makes the graceful exit concrete. It defaults to **`max_steps=500`**. At 75% of that it injects a "BUDGET WARNING" telling the agent to consolidate results, because "partial results are far more valuable than exhausting all steps with nothing saved." On the final step it rebuilds the action schema so **`done` is the only available action** ([browser-use service.py](https://github.com/browser-use/browser-use/blob/main/browser_use/agent/service.py)).

| System | Default step cap | At the cap | What really bounds long work |
|---|---|---|---|
| OpenAI Agents SDK | 10 turns (`None` disables) | Exception, or handler returns final output | Integrator's choice |
| Codex Goals | None | `budget_limited` wrap-up turn | Token/time budget, blocked audit, user pause |
| xAI API agent loop | Undisclosed server default | Forced final synthesis, no error | Caller's outer loop |
| Grok Bot | None published | n/a | Weekly usage and spend limits |
| LangGraph 1.2.x | 10007 supersteps per invocation | `GraphRecursionError`, or `RemainingSteps` routing to wrap-up | Thread-level call limits, resumable threads |
| browser-use | 500 steps | 75% warning, then done-only final step | Loop/stall nudges, failure count, judge |

The bot's 24 passes per run is therefore a self-imposed limit, not a framework one. And because the cap is 5 chunks rather than a budget, the bot stops at an arbitrary point instead of a meaningful one.

## Progress classification decides when to stop, not step count

The most complete published stopping logic is Codex's goal continuation prompt. After every turn, the model must classify the previous turn as **"progress, a verified wait, or no progress"**. Progress "changes authoritative state, completes work, or yields evidence that changes the next action". By contrast, "status restatements and unexecuted plans are no progress." A goal may be marked `blocked` **only after the same blocking condition repeats for at least three consecutive goal turns**. Equivalent blockers count as the same condition "even when their wording or stated next step changes". The prompt forbids marking a goal blocked "merely because the work is hard, slow, uncertain" ([continuation.md](https://github.com/openai/codex/blob/main/codex-rs/ext/goal/templates/goals/continuation.md)). Two runtime guards back this up. A continuation turn that makes no tool call suppresses the next automatic continuation "so Codex does not spin" ([Goals cookbook](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)). An empty model response moves the goal to `Blocked` rather than looping ([runtime.rs](https://github.com/openai/codex/blob/main/codex-rs/ext/goal/src/runtime.rs)).

Codex is equally strict about the other end. Its completion audit tells the model to "treat completion as unproven", to inspect current state for every explicit requirement, and to treat indirect evidence as not achieved. It forbids marking done "merely because the budget is nearly exhausted" and forbids redefining success "around a smaller or easier task" ([continuation.md](https://github.com/openai/codex/blob/main/codex-rs/ext/goal/templates/goals/continuation.md)). browser-use reaches the same goal with a separate LLM judge, on by default. The judge reads the task, the step log and up to the last 10 screenshots, and returns a verdict plus flags for `impossible_task` and `reached_captcha` ([judge.py](https://github.com/browser-use/browser-use/blob/main/browser_use/agent/judge.py)). Anthropic's long-running harness writes a JSON feature list up front, in which the agent may only flip `passes`. JSON was chosen because the model is "less likely to inappropriately change or overwrite" it ([Anthropic harness post](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). Separate verifiers pay off measurably: OpenHands' critic raised SWE-bench Verified from **60.6% to 66.4%** ([OpenHands blog](https://www.all-hands.dev/blog/sota-on-swe-bench-verified-with-inference-time-scaling-and-critic-model)).

Action-level loop detection comes from the open-source side, not the vendors. xAI documents no loop detection anywhere. Its answer to a stuck Bot is visibility and cheap human redirection ([Grok Bot Troubleshooting](https://docs.x.ai/grok-bot/troubleshooting)). OpenAI documents none for ChatGPT agent. LangGraph and LangChain ship no loop detector either. The `LoopDetectionMiddleware` described in LangChain's harness-engineering post is unpublished. That post's harness changes, which included loop nudges, pre-completion verification and time-budget warnings, moved Terminal Bench 2.0 from **52.8% to 66.5%** with no model change ([LangChain blog](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering)). browser-use's `ActionLoopDetector` is explicitly soft: it "never blocks actions." It hashes normalized actions over a 20-action window and escalates nudges at 5, 8 and 12 repeats. A separate page fingerprint (URL, interactive-element count, DOM-text hash) warns after **5 unchanged pages**. After 3 consecutive failures, the agent is told to output a new plan ([views.py](https://github.com/browser-use/browser-use/blob/main/browser_use/agent/views.py)). OpenHands' `StuckDetector` covers repeated action and observation (4), the same action erroring (3), monologue (3), A-B-A-B alternation (6) and context-error loops. For the error streak, it nudges once before declaring the agent stuck ([stuck_detector.py](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/stuck_detector.py)).

All of these thresholds are engineering defaults. None of the sources publishes an A/B measurement of them, and no study compares fixed step caps against adaptive budgets for web agents. Two known false positives matter for the bot. browser-use hashes clicks by element index, which misses loops when elements are renumbered; the in-house bot's label-based comparison already avoids this. Repeated waits or screenshots also trip loop and stagnation detectors ([Cursor forum](https://forum.cursor.com/t/how-to-disable-loop-detection/142696)). So declared waits and observation-only steps must be excluded from detection.

### Waiting is a state, not a stream of steps

Codex's rule for slow external work fits the bot's 20-step wait on Claude Research almost exactly: "A verified wait polls a specific process, session, job, or tool handle confirmed live now… An observation timeout or transient polling failure is not terminal… never restart solely because observation expired" ([continuation.md](https://github.com/openai/codex/blob/main/codex-rs/ext/goal/templates/goals/continuation.md)). A verified wait counts as progress, so it uses up neither the no-progress counter nor patience. At the API layer, OpenAI runs long work with `background: true` and polling, and keeps it alive while the client is disconnected ([Background mode guide](https://developers.openai.com/api/docs/guides/background)). xAI's deferred completions return a `request_id` that can be polled for up to 24 hours ([xAI Deferred completions](https://docs.x.ai/docs/guides/deferred-chat-completions)). Grok Bot's background turns survive closing the app ([Grok Bot FAQ](https://docs.x.ai/grok-bot/faq)). UI agents cap individual waits at 30 s in browser-use and 300 s in Anthropic computer use ([browser-use tools/service.py](https://github.com/browser-use/browser-use/blob/main/browser_use/tools/service.py), [Claude computer use docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)). No source measures polling cadence for multi-minute UI jobs. The design the evidence supports is to have the harness poll a cheap completion signal without LLM calls, and to suspend and wake later for anything long.

## Handoff summaries and observation masking keep long trajectories coherent

Every vendor compacts, but they differ in who triggers it. OpenAI's Responses API compacts **automatically on the server** once rendered tokens cross a `compact_threshold`; the examples use 200,000. It emits an opaque encrypted item and continues within the same response ([Compaction guide](https://developers.openai.com/api/docs/guides/compaction)). xAI's `POST /v1/responses/compact` is **client-triggered only**, "every N turns inside an agent loop" or on your own threshold. xAI recommends a smaller, faster model for frequent compaction, and notes that compaction "cannot rescue a request past `context_length_exceeded`" ([xAI Context Compaction](https://docs.x.ai/developers/advanced-api-usage/context-compaction)). Encrypted compaction items only work with their own vendor's models, so a DeepSeek bot has to reproduce the plaintext version. Codex shows what that looks like. Its compaction prompt asks for "a handoff summary for another LLM that will resume the task" covering progress and key decisions, constraints and user preferences, remaining next steps, and critical data and references ([compact prompt.md](https://github.com/openai/codex/blob/main/codex-rs/prompts/templates/compact/prompt.md)). After compaction, the continuation prompt says to "use the current worktree and external state as authoritative… inspect the current state before relying on it" ([continuation.md](https://github.com/openai/codex/blob/main/codex-rs/ext/goal/templates/goals/continuation.md)). For a browser bot, that means re-observing the live page instead of trusting the summary.

Summaries fail in a predictable way: they drop the fact that something was already tried, or they mark half-done work as done. Users have reported Codex "losing the plot" after auto-compaction ([codex issue via upd.dev](https://upd.dev/openai/codex/issues/5957)). browser-use's summarizer guards against this explicitly: "Only mark a step as completed if you see explicit success confirmation in the history… Never infer completion from context." It compacts every 25 steps once history exceeds 40,000 characters, keeps the last 6 items verbatim, and caps the summary at 6,000 characters ([message_manager/service.py](https://github.com/browser-use/browser-use/blob/main/browser_use/agent/message_manager/service.py), [views.py](https://github.com/browser-use/browser-use/blob/main/browser_use/agent/views.py)). LangChain packages the same building blocks as middleware. `SummarizationMiddleware` takes token, fraction or message triggers, and `ContextEditingMiddleware` clears old tool outputs while keeping the last 3. Deep Agents additionally writes evicted history to `/conversation_history/` and moves tool results over 20,000 tokens to files, leaving a pointer ([Built-in middleware](https://docs.langchain.com/oss/python/langchain/middleware/built-in), [deepagents summarization.py](https://github.com/langchain-ai/deepagents/blob/main/libs/deepagents/deepagents/middleware/summarization.py)).

The cheapest technique is also the best measured. On SWE-bench Verified, simple **observation masking halves cost** relative to the raw agent and matches LLM summarization's solve rate, and a hybrid saves a further 7–11% ([The Complexity Trap](https://arxiv.org/abs/2508.21433)). Manus adds three cache-aware rules. Keep the prefix stable and context append-only, because the KV-cache hit rate is "the single most important metric for a production-stage AI agent". Recite a todo list at the end of context to counter lost-in-the-middle drift. Keep failed actions visible, because "seeing failures shifts the model's beliefs away from repeating similar mistakes" ([Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)). Anthropic's computer-use guidance on screenshots is to keep the last three and prune in batches every 25 turns, so the cache prefix survives ([Claude computer use docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)). xAI's pricing adds a cost reason to compact early: on grok-4.7, crossing 200k prompt tokens doubles the rate on **all** tokens in the request ([xAI Models & pricing](https://docs.x.ai/developers/models)).

## Durable threads, interrupts and takeover replace "say continue"

LangGraph already provides what the bot's chunk mechanism rebuilds by hand. With a Postgres checkpointer, state is saved at every superstep. Completed sibling writes are not re-run, and a crashed or paused thread resumes when you invoke it again with `None` (or `Command(resume=...)`) on the same `thread_id` ([Checkpointers docs](https://docs.langchain.com/oss/python/langgraph/checkpointers)). Durability defaults to `"async"`. `"sync"` persists before the next step starts, which is the right choice when steps click real buttons. Resumed nodes re-run from their start, so actions must be idempotent ([types.py](https://github.com/langchain-ai/langgraph/blob/main/libs/langgraph/langgraph/types.py), [Graph API docs](https://docs.langchain.com/oss/python/langgraph/graph-api)). `interrupt(payload)` pauses a node indefinitely at zero cost, and `Command(resume=value)` continues it ([Interrupts docs](https://docs.langchain.com/oss/python/langgraph/interrupts)). That is the natural primitive for login, CAPTCHA and approval walls. The hosted Agent Server adds `multitask_strategy` for messages that arrive mid-run. Its `interrupt` strategy halts the run, keeps progress, inserts the new input and continues, and the graph must handle tool calls left dangling. This "double-texting" is **not available in open-source LangGraph** ([Double-texting docs](https://docs.langchain.com/langsmith/double-texting)), so the bot's steering must stay home-grown. Deep Agents' `PatchToolCallsMiddleware` shows the repair step it needs ([deepagents graph.py](https://github.com/langchain-ai/deepagents/blob/main/libs/deepagents/deepagents/graph.py)).

The products layer human control on top in three ways. ChatGPT agent pauses for confirmation before state-changing actions, with **100% critical-confirmation recall on financial transactions**. Its Watch Mode stays on in logged-in sensitive contexts and auto-pauses when the user goes idle or leaves ([Deployment Safety Hub](https://deploymentsafety.openai.com/chatgpt-agent/watch-mode)). Grok Bot has the user "take control, complete only the blocked step, and tell the Bot to continue" for passwords, 2FA, CAPTCHAs and payments, and it should "pause and notify" when a session expires ([Grok Bot computer and apps](https://docs.x.ai/grok-bot/computer-and-apps)). Codex constrains who may change a goal's lifecycle. The model may only start a goal or mark it complete. Pause, resume and budget transitions belong to the user or the system, and the model must "never pause on your own initiative" ([Goals cookbook](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)). The OpenAI Agents SDK serializes paused runs (`RunState.to_json`) for durable approvals. It requires replay protection so that a submission cannot resume the same snapshot twice ([Human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/)). In all of these, a pause is a state the task resumes from without losing progress. None of them asks the user to type "continue".

## Malformed output becomes an error observation, and DeepSeek has a known cause

The frameworks agree that a bad model output should cost one retry, not the run. OpenAI's Agents SDK returns tool exceptions and timeouts to the model by default (`timeout_behavior="error_as_result"`). It can also return unknown tool names to the model (`tool_not_found_behavior="return_error_to_model"`) ([Tools docs](https://github.com/openai/openai-agents-python/blob/main/docs/tools.md), [Running agents](https://openai.github.io/openai-agents-python/running_agents/)). LangChain's `ToolStrategy(handle_errors=...)` feeds validation errors back as a ToolMessage. The catch is that it validates only Pydantic, dataclass or TypedDict schemas, not raw JSON-schema dicts ([structured_output.py](https://github.com/langchain-ai/langchain/blob/master/libs/langchain_v1/langchain/agents/structured_output.py)). `ToolNode` returns argument errors with "Please fix the error and try again." ([tool_node.py](https://github.com/langchain-ai/langgraph/blob/main/libs/prebuilt/langgraph/prebuilt/tool_node.py)). browser-use tolerates 5 consecutive failures and then switches to a `fallback_llm` for the rest of the run ([browser-use docs](https://docs.browser-use.com/customize/agent/all-parameters)).

The bot's XML-tag failure matches a documented DeepSeek behaviour. DeepSeek V3.2 and V4 emit tool calls in an internal XML-like **DSML** grammar (`<|DSML|tool_calls>` with `invoke`/`parameter` elements) ([vLLM DeepSeek V4 tool parser](https://docs.vllm.ai/en/v0.21.0/api/vllm/tool_parsers/deepseekv4_tool_parser/)). Users report whole responses arriving as DSML text in `content` with no structured `tool_calls` ([HF DeepSeek-V4-Pro discussion #209](https://huggingface.co/deepseek-ai/DeepSeek-V4-Pro/discussions/209), [LangChain forum](https://forum.langchain.com/t/the-output-content-has-been-corrupted/3551)). DeepSeek's official mitigation is **strict-mode tool calls** on the `/beta` base URL. These are validated server-side, work in thinking and non-thinking modes, and require every property in `required` plus `additionalProperties: false` ([DeepSeek Tool Calls guide](https://api-docs.deepseek.com/guides/tool_calls)). A community guide warns that setting `strict` on the default base URL silently does nothing ([horadecodar.com.br](https://horadecodar.com.br/?p=41360)). If the bot stays on JSON mode, DeepSeek requires the word "json" and an example in the prompt, enough `max_tokens`, and handling for occasional empty content ([DeepSeek JSON Output guide](https://api-docs.deepseek.com/guides/json_mode)). Thinking mode adds one more requirement: assistant messages that precede tool calls must carry their `reasoning_content`, or the API returns HTTP 400 ([Zed commit](https://git.secluded.site/zed/commit/5dd8561b06c8af4ee46f3aa8bcf839f208b8c7bf)). No source measures how drift scales with prompt length, and the end-of-prompt reminder the bot now uses is practitioner advice, not a measured fix. Shrinking the page listing attacks the probable trigger directly.

## Saved skills are the best-measured lever for repeat web tasks

Procedural memory has the strongest quantitative evidence of anything in this report. Agent Workflow Memory induces reusable workflows from past trajectories. It improved success by **51.1% relative on WebArena and 24.6% on Mind2Web, with fewer steps** ([AWM](https://arxiv.org/abs/2409.07429)). SkillWeaver practices and distills site skills into APIs, gaining **31.8% on WebArena and 39.8% on real sites**. Skills built by strong agents lifted weaker agents by up to **54.3%** ([SkillWeaver](https://arxiv.org/abs/2504.07079)). That transfer result is directly relevant to running v4-pro skills on cheaper DeepSeek tiers. Agent KB adds "feedback-time" retrieval of fixes when execution goes wrong, a measured form of looking things up when stuck ([Agent KB](https://arxiv.org/abs/2507.06229v3)). ExpeL stores natural-language insights from failures as well as successes ([ExpeL](https://arxiv.org/abs/2308.10144)).

The products treat learned procedure cautiously. Grok Bot skills are documents covering "when to use it, inputs and access, the sequence of steps, validation, what to return, and what needs approval". A skill recorded from a demonstration "is a draft" until decision rules, failure handling and approval boundaries are added. xAI's recommended progression is one-off task, then reliable task, then saved skill, then scheduled routine ([Grok Bot Skills and routines](https://docs.x.ai/grok-bot/skills-routines-and-automations)). OpenAI disabled ChatGPT memory in agent mode at launch to limit prompt-injection exfiltration ([Deployment Safety Hub](https://deploymentsafety.openai.com/chatgpt-agent/watch-mode)). Codex's rollout-mined memories are **off by default** and include a `disable_on_external_context` switch ([Codex config reference](https://learn.chatgpt.com/docs/config-file/config-reference)). LangMem offers background reflection and prompt optimizers over scored trajectories, but at version 0.0.x its API is unstable ([LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)). The common lesson is to learn from runs a verifier judged successful, never from instructions found in page text, and to keep skills as editable documents.

## Redesign blueprint for the DeepSeek browser bot

The bot already has most of the components: plan and notes, label-based repeat warnings, model tiers, a vision glance, steering, approvals, check_back, skill memories and web_search. What it lacks is the control logic that ties them together. The redesign below keeps the per-run ceilings as safety nets and changes what ends a task.

| Today | Change | Pattern it follows |
|---|---|---|
| Stop after 5 chunks, ask person to say "continue" | Task-level budget (cost, wall clock, LLM calls) persisted across chunks; warning at 75%; forced done/handoff-only final step; `budget_limited` state with a one-tap "extend" | Codex budget_limit, browser-use 75% warning and done-only step, LangChain thread_limit |
| 24 passes per run ends the chunk | Chunk ends when context crosses a token threshold or the per-run ceiling is near (`RemainingSteps`-style routing); next chunk resumes the same LangGraph thread from the checkpoint | LangGraph resume semantics, OpenAI token-triggered compaction |
| Step log of last lines carried over | Structured handoff summary: progress, decisions, constraints, tried-and-failed approaches, remaining steps, critical data; "never infer completion"; first action of a new chunk re-observes the page | Codex compact prompt, browser-use summarizer, Codex re-grounding |
| No notion of progress across chunks | At each chunk end, classify progress / verified wait / no progress; stop as `blocked` and ask the person only after 3 consecutive no-progress chunks or the same blocker 3 times | Codex continuation audit |
| Repeated-action warning | Keep label hashing; add page fingerprint (URL + element count + text hash, 5 unchanged); escalate nudge → think tier + glance → help-doc web_search → ask person; same action + same error 3× nudges once, then escalates | browser-use, OpenHands, Agent KB |
| ~20 "wait 30s" steps | `wait_for(signal, expected_duration)` polled by the harness with backoff and a DOM/text check, no LLM calls; waits over a few minutes go through check_back/wakes; excluded from loop detectors and step counts, charged to wall clock | Codex verified wait, OpenAI background mode |
| JSON reminder + tag fallback parser | Native tool calls with `strict: true` on `/beta`; parse order tool_calls → DSML → lenient JSON → re-ask with the parse error → fall back to a non-thinking or flash tier for that step; only after that, mark "confused/blocked" | DeepSeek docs, vLLM DSML parser, browser-use fallback_llm |
| Full ~15k-token page each step | Full listing only for the current step; older observations masked to one line (URL, action, result); last 2–3 screenshots; large pages offloaded to notes; plan recited at the end of the prompt; stable prefix for caching | Complexity Trap, Manus, Anthropic screenshot pruning |
| Self-declared completion | Evidence audit or cheap judge over the step log and last screenshots before `done`; no shrinking the request | Codex completion audit, browser-use judge |
| Skill memories | After a judged success, distill a site-scoped skill (trigger, steps with variables, validation, approval points, pitfalls) plus failure lessons; retrieve by domain at task start; fold help-doc lookups into it; treat as draft until reused successfully | AWM, SkillWeaver, Grok Bot skills |

Three design choices deserve emphasis. The first is the budget numbers. The bot's current worst case is 5 × $3 = **$15** and 5 × 30 min = **2.5 hours**, so a task-level default at that level spends no more than today. The difference is that it never stops a task that is still progressing before the budget runs out, and it stops a looping task far earlier through the no-progress counter. The second is that the lifecycle should be explicit and owned by the system, as in Codex. States are active, waiting, paused (human), blocked, budget_limited and complete. The model may propose complete or blocked, but only the harness and the person move the task between the other states. Mid-run steering should follow the Agent Server `interrupt` strategy, implemented in-house: finish or patch the in-flight action, insert the message, continue on the same thread. Login and CAPTCHA walls should use `interrupt()` with takeover rather than consuming a chunk. Use `durability="sync"`, because a replayed click on a real site is not idempotent. The third is that most of this reduces DeepSeek's failure surface as well as cost. Shorter prompts from masking, strict tool schemas and a fallback tier address the exact conditions (long page, thinking on) under which the XML drift appeared.

Some uncertainty remains. The nudge thresholds (5/8/12 repeats, 5 unchanged pages, 3 blocked turns) are untested defaults borrowed from other systems and should be tuned on the bot's own traces. ChatGPT agent's internal per-task limits and Grok Bot's internal caps are undocumented, so "no step cap" there means "none published". The skill-reuse gains come from benchmarks, not from DeepSeek-driven production browsing.

## Conclusion

The question has shifted from "how many steps should the bot get" to "how does the bot know it is still getting somewhere". Every mature system answers the second question with a separate, auditable signal: a semantic progress classification, a page that has stopped changing, a verifier, or a person. They also make running out of budget a polite handoff rather than a cutoff. The chunk-and-continue design was a reasonable substitute for durable execution, but LangGraph's resumable threads already provide that, so chunks can become a context-hygiene boundary instead of a stop point.

The largest gains will probably come from what happens after a task succeeds, not from tuning the loop. The evidence on distilled workflows (31–51% relative on WebArena) outweighs anything measured for loop detection or compaction. The bot already stores a "skill" memory kind. Making the judge-confirmed site playbook the default output of every successful long task is the change most likely to make the next long task short.
